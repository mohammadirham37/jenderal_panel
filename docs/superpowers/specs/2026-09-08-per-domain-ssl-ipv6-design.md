# Per-Domain SSL and Automatic IPv6 Detection Design

## Context

Jenderal Panel currently renders every website virtual host with an IPv6
listener. On VPS instances where IPv6 is disabled at kernel level, `nginx -t`
fails with `socket() [::]:80 failed (97: Address family not supported by
protocol)`. The installer works around the same problem only for the default
Nginx site, so every PHP or static website generated by the panel can still
fail.

The existing SSL module already contains a Let's Encrypt client and certificate
records, but the feature is not usable end to end:

- the frontend posts to `/api/v1/ssl`, while the backend exposes
  `/api/v1/ssl/issue`;
- the generated HTTPS server includes a `.location` file that is never created;
- the auto-renew toggle calls a route that is not registered;
- arbitrary domains are accepted without proving that they belong to the
  selected website;
- custom certificates are not supported; and
- HTTPS configuration also assumes IPv6 is available.

This design fixes the IPv6 failure and completes a secure, per-domain SSL flow
for both free Let's Encrypt certificates and operator-provided certificates.

## Goals

- Detect IPv6 support automatically and emit IPv6 listeners only when the host
  can open them.
- Install Let's Encrypt certificates for a primary or alias domain registered
  to an existing website.
- Install custom certificate chains and private keys pasted into the panel.
- Redirect HTTP to HTTPS for a domain only after its certificate and Nginx
  configuration have been validated and activated.
- Keep ACME HTTP-01 challenge paths available over HTTP.
- Preserve the previous working certificate and configuration when replacement
  or Nginx activation fails.
- Keep certificate lifecycle state visible on the existing SSL Certificates
  page.

## Non-Goals

- Managing certificates for arbitrary domains that are not registered to a
  panel website.
- DNS-01 challenges or wildcard issuance through Let's Encrypt.
- Automatic renewal of custom certificates.
- Replacing Nginx with another reverse proxy or allowing Certbot to rewrite
  panel-owned configuration.
- Storing private keys in SQLite, API responses, or audit logs.

## Chosen Approach

Extend the existing SSL service and website renderer. Both Let's Encrypt and
custom input feed one certificate activation pipeline. Application routing is
rendered by shared HTTP/HTTPS templates instead of including an external
location file. This retains the current application architecture, avoids a new
system dependency, and keeps Nginx configuration ownership inside the panel.

Using Certbot was rejected because it adds a package dependency and gives a
second component permission to mutate panel-managed virtual hosts. Moving TLS
termination to Caddy or Traefik was rejected because it would be a much larger
proxy migration.

## IPv6 Capability Detection

A small Nginx capability helper will inspect `/proc/net/if_inet6`. IPv6 is
considered available only when that file can be read and contains at least one
interface entry. Read errors and empty content are treated as IPv6 unavailable,
which is the safe behavior for Linux VPS environments.

The detector result is passed explicitly into render data. It controls all
panel-generated IPv6 listeners:

- website HTTP port 80;
- website HTTPS port 443; and
- future renderers using the shared capability.

IPv4 listeners are always emitted. Detection occurs when configuration is
generated, so retrying a failed website after updating the panel regenerates a
compatible virtual host without requiring a reinstall.

The detector is isolated behind a function whose file path/input can be
controlled in tests. Production always uses `/proc/net/if_inet6`.

## Website and HTTPS Rendering

The website renderer will support three server variants from the same
application data:

1. One HTTP application server contains only the primary/alias domain names
   that do not yet have active certificates, plus the existing PHP/static
   routing.
2. Each domain with an active certificate gets a small exact-name HTTP server.
   Its `/.well-known/acme-challenge/` location is served from the document root
   and every other path returns `301 https://$host$request_uri`.
3. The HTTPS application server is rendered per certificate domain with its
   certificate paths and the same PHP/static application routing. For aliases,
   the PHP-FPM socket continues to use the website's primary domain pool.

The SSL service loads the website, all registered domains, and the set of
active certificate domains before rendering. It never interpolates an
unregistered request domain into a path or Nginx directive.

Installing or removing a certificate re-renders the HTTP virtual host so that
domains move between the application server and their exact redirect server.
This avoids conflicting `server_name` declarations and ensures direct PHP/file
paths cannot bypass HTTPS. Other aliases continue to work over HTTP.

## API Contract

Existing authenticated RBAC permissions remain in use.

### Let's Encrypt

`POST /api/v1/ssl/issue`

```json
{
  "website_id": "website-id",
  "domain": "example.com"
}
```

The frontend will be corrected to use this existing route.

### Custom SSL

`POST /api/v1/ssl/custom`

```json
{
  "website_id": "website-id",
  "domain": "example.com",
  "certificate_pem": "-----BEGIN CERTIFICATE-----...",
  "private_key_pem": "-----BEGIN PRIVATE KEY-----..."
}
```

For a domain with an existing certificate, custom installation is treated as
an atomic replacement. The existing certificate record is reused where
possible so the UI maintains one logical record per website/domain.

### Auto-Renew

`PUT /api/v1/ssl/{id}`

```json
{
  "auto_renew": true
}
```

Only Let's Encrypt certificates accept auto-renew changes. Custom certificates
always store `auto_renew=false`.

Existing list, get, renew, revoke, and delete routes remain compatible. Manual
renewal applies only to Let's Encrypt certificates. Custom certificates expose
Replace instead.

## Domain Ownership and Certificate Validation

Before either installation mode begins, the service verifies that the requested
domain is a primary or alias domain belonging to `website_id`.

For custom input, validation completes before any live file is changed:

- both PEM fields are required and size-bounded;
- `tls.X509KeyPair` verifies that the private key matches the leaf certificate;
- the leaf certificate is parsed with `crypto/x509`;
- `VerifyHostname` checks the selected domain, including standard wildcard
  matching;
- `NotBefore` must not be in the future and `NotAfter` must be in the future;
- the submitted certificate text may contain the full intermediate chain; and
- the displayed expiration date is taken from the parsed leaf certificate.

Let's Encrypt responses are parsed through the same certificate metadata
function. Expiration is read from the issued certificate instead of assuming a
fixed 90-day lifetime.

Private-key content is never included in error messages or audit details.

## Certificate Activation and Rollback

The shared activation pipeline performs these steps:

1. Validate website/domain ownership and certificate material.
2. Create unique temporary files with mode `0600` and register unconditional
   cleanup.
3. Snapshot any existing domain certificate files plus HTTP/HTTPS virtual-host
   files.
4. Write certificate and key files under the panel certificate directory. The
   private key remains mode `0600`.
5. Render the per-domain HTTPS server and the updated HTTP server.
6. Run `nginx -t`.
7. Reload Nginx.
8. Only after successful reload, commit the active certificate metadata and
   website SSL state in SQLite.

If steps 4-7 fail, the snapshot is restored, `nginx -t` is run against the
restored configuration, and the previous configuration is reloaded. A first
installation retains a failed certificate record and sanitized error message
for troubleshooting. A failed replacement leaves the previous record active
and reports the replacement error without discarding the working certificate.

Nginx continues serving its previously loaded configuration while a candidate
configuration is being validated.

## Certificate Lifecycle Semantics

- `issuer` is `letsencrypt` or `custom`.
- Let's Encrypt certificates default to `auto_renew=true`.
- Custom certificates always use `auto_renew=false` and are excluded from the
  renewal worker.
- ACME revocation is called only for Let's Encrypt records. Revoking or deleting
  a custom certificate removes its local files/configuration without contacting
  ACME.
- `websites.ssl_enabled` is true when at least one active certificate remains
  for that website. Revoke/delete recomputes this value rather than clearing it
  unconditionally.
- Service-level transactional checks maintain one current logical certificate
  record per website/domain without requiring a schema migration. Existing
  historical duplicate rows remain readable and can be deleted normally.

## Frontend Experience

The existing SSL Certificates page remains the management surface.

The installation form contains:

- a website dropdown;
- a domain dropdown populated only from that website's primary and alias
  domains;
- a method toggle: **Let's Encrypt (Free)** or **Custom SSL**;
- for custom mode, a Certificate / Full Chain PEM textarea and a Private Key
  PEM textarea; and
- a single context-aware Install/Replace action.

Sensitive textarea values are cleared when the form closes or an installation
succeeds. They are not placed in local storage. Errors identify the invalid
field without echoing submitted PEM data.

The certificate table shows issuer, status, and parsed expiry. Auto-renew and
Renew are available only for Let's Encrypt. Custom records show Replace. The
website detail page shows SSL status and links to the SSL Certificates page; it
does not duplicate the installation form.

## Compatibility

- No database migration is required; the existing `issuer`, `expires_at`, and
  `auto_renew` columns represent both certificate types.
- Existing Let's Encrypt records and routes remain readable.
- Static and PHP websites retain their current application routing.
- IPv6-capable hosts retain dual-stack listeners; IPv4-only hosts omit them.
- Retrying the currently failed website after the panel update regenerates its
  configuration using the detected capability.

## Testing

Backend tests will cover:

- IPv6 capability detection for populated, empty, and unavailable probe files;
- HTTP and HTTPS rendering with IPv6 enabled and disabled;
- PHP socket routing for primary and alias certificate domains;
- exact-domain HTTPS redirect with an HTTP ACME exception;
- rejection of domains not owned by the selected website;
- valid custom chains plus mismatched key, malformed PEM, wrong hostname,
  not-yet-valid, and expired cases;
- actual expiration parsing for both Let's Encrypt and custom certificates;
- successful custom installation and atomic replacement;
- rollback when `nginx -t` or reload fails;
- issuer-aware renew/revoke behavior;
- recomputation of `websites.ssl_enabled`; and
- API route/status validation for issue, custom install, and auto-renew.

Frontend tests will cover method switching, registered-domain selection,
endpoint/payload selection, secret-field clearing, and issuer-specific actions.
The final gate is the complete Go test suite, `go vet`, frontend tests,
`svelte-check`, and production build.

## Rollout and Operator Recovery

The change ships through the existing panel updater. After updating an
IPv4-only VPS, the operator clicks Retry on the failed website; provisioning
re-renders the virtual host without IPv6 and validates Nginx again.

SSL installation is then available from SSL Certificates. The UI does not mark
a domain active until Nginx validation and reload succeed. Failures retain a
visible sanitized status while the last working configuration remains active.
